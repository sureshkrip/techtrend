<objective>
Fix source-blind enrichment grounding so Hacker News, npm, PyPI, and changelog
items get summarized and filed into a sidebar section — not just GitHub repos.

Root cause (established, verified against prod): `grounding.py::fetch_grounding`
unconditionally hits `GET api.github.com/repos/{full_name}` using the entity's
`full_name` as an `owner/repo` path. For non-GitHub entities `full_name` is a
headline / package name / feed label, so the GitHub call 404s, the exception
propagates into `run_enrichment`'s per-candidate try/except, and the candidate
is silently skipped — no enrichments row, no summary, no section, so it never
appears under any sidebar section. Prod confirms: enrichments has ONLY github
rows; zero hn/npm/pypi/changelog rows have ever been written.

Fix: make grounding dispatch on `entities.source`, with an honest,
source-appropriate grounding strategy per source (below), reusing the existing
GitHub path unchanged for `source='github'`. Thread `source` + `url` through
`select_candidates` → `run_enrichment` → the injectable `fetch_grounding_fn`
seam. Selection stays source-agnostic; only the FETCH becomes source-aware.

Purpose: Restore the core value — HN/npm/PyPI/changelog momentum actually gets
classified into the seven sections instead of vanishing.
Output: Source-aware `grounding.py`, rewired `enrich.py`, and fixture-backed
tests covering every source path (no live network anywhere).

Scope boundary: This is the CATEGORIZATION (grounding+enrichment) fix ONLY. The
dashboard source-split/filter UI is a SEPARATE follow-up quick task and is NOT
in scope here.
</objective>

<grounding_strategy>
The single most important design decision in this plan is the grounding
strategy per source. Each is justified against the anti-fabrication rule (D-08:
never summarize from nothing; if there is genuinely nothing real to ground on,
write a fetch_failed tombstone rather than invent). The entities table stores
NO rich body text (only source, full_name, url, homepage, docs_url, ...), so
each source either grounds on already-stored fields or fetches source-
appropriate first-party text. No DB schema migration is needed or proposed.

- github (UNCHANGED): GitHub metadata `description` + README intro via the
  authenticated GitHub client. Preserved byte-for-byte (see Task 1).

- hn: ground on `full_name`, which for HN IS the real story TITLE (see
  hn.py::normalize — `full_name=raw["title"]`). NO network fetch. The title is
  genuine, already-stored, non-fabricated text describing the item, so D-08 is
  satisfied by grounding on it. description=title, body="". Return None (→
  tombstone) only if the title is empty/whitespace (should never happen — HN
  requires a title). Rationale for NOT fetching the linked article: the schema
  stores no body, arbitrary web-article extraction needs a scraping/readability
  layer the project deliberately excludes (CLAUDE.md "What NOT to Use": no
  scrapy), and the headline alone is enough real text to classify + summarize.

- npm: fetch the first-party packument `GET https://registry.npmjs.org/{pkg}`
  via the UNAUTHENTICATED public client (build_public_client). Use top-level
  `description` + the top-level `readme` (run through the existing extract_intro
  H2-truncation + char_cap). This mirrors the GitHub metadata+README shape with
  real first-party text, so D-08 holds. If both description AND readme are
  empty/missing (or the package 404s / is unpublished) → return None →
  tombstone. Scoped packages (`@org/pkg`) must URL-encode the slash as `%2F`
  (mirror packages.py's `quote(package, safe="@")`).

- pypi: fetch `GET https://pypi.org/pypi/{pkg}/json` via the public client. Use
  `info.summary` as description + `info.description` (long text) run through
  extract_intro + char_cap as body. NOTE this is a DIFFERENT endpoint than the
  pypistats `recent` endpoint the collector uses — pypistats has no description;
  pypi.org's JSON API does. If both summary AND description empty (or 404) →
  None → tombstone.

- changelog: `full_name` is the curated feed LABEL and `url` is the feed URL.
  Re-parse the feed with feedparser (grounding is explicitly a "fresh fetch",
  not a collector) and ground on real in-feed content: description = the feed's
  own title (`parsed.feed.get("title")`, falling back to the label) + body =
  the most-recent entry titles joined (capped to char_cap). If the feed is bozo
  / unreachable / has zero entries → None → tombstone. Grounding on entry titles
  (real feed content) rather than the bare label keeps D-08 honest.

For npm/pypi, a hard 404 is caught INSIDE the grounding function and treated as
"nothing to ground on" (return None → tombstone), mirroring how
`_get_readme_text` already catches a 404 README as None — rather than letting it
raise into the outer loop (which would skip the candidate with no row at all).
Transient 429/5xx keep retrying via the existing `is_retryable_public`
predicate.
</grounding_strategy>

<key_decisions>
Locked design decisions the executor MUST honor:

1. **`select_candidates` selection logic is UNCHANGED.** Only add
   `entities.source` and `entities.url` to the SELECT column list of
   `_SELECT_CANDIDATES_SQL`. Do NOT touch the WHERE clause, the eligible-set
   join, the `ORDER BY wilson_lower_bound DESC, entities.id ASC`, or the
   `LIMIT %(enrichment_cap)s`. The bug is in the FETCH, not selection — do not
   narrow selection.

2. **The GitHub path is preserved exactly.** Extract the current
   `fetch_grounding` body verbatim into `_fetch_github_grounding(client,
   full_name, char_cap)` and route `source='github'` to it. Same metadata+README
   fetch, same "both empty → None", same reliance on the caller's
   normalize_for_hash badge stripping and cache-hit skip.

3. **The LLM call is UNCHANGED — do NOT touch `enrich_item` /
   `enrich_item_openai` signatures or their prompt.** The dispatcher returns a
   `(description, body_text)` tuple that maps onto the existing
   `(description, readme_intro)` kwargs. The prompt's `<repo_description>` /
   `<readme_excerpt>` tags are just data containers; they function correctly for
   headlines/registry text/feed titles. Rewording the prompt is out of scope and
   risks the confined-literal greps in llm_openai.py.

4. **No new tunable, no schema migration.** Reuse the existing
   `Tunables.grounding_char_cap` (already threaded as `char_cap`) for every
   source's truncation. Reuse the existing content-hash / cache-hit machinery
   unchanged (it already operates on any (description, body) pair).

5. **Both HTTP clients are built once per run.** `run_enrichment`'s production
   seam builds `build_client()` (authenticated, github) AND
   `build_public_client()` (unauthenticated, npm/pypi) up front — never per
   candidate — inside the existing `if fetch_grounding_fn is None` block, which
   already only runs when the candidate set is non-empty (so a zero-candidate
   run still needs no clients/tokens). Changelog needs no httpx client
   (feedparser manages its own I/O).
</key_decisions>
