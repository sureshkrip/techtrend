<objective>
Turn accumulated snapshots into a defensible ranking: velocity over a trailing window, gated by an absolute floor on stars gained, ordered by a Wilson lower confidence bound, with the cross-source normalization seam built and the day-to-day stability of the result measured rather than assumed.

Purpose: This is the slice that makes the dashboard show *genuine velocity* instead of raw star count — Phase 1's whole reason for existing before any LLM spend. RESEARCH.md's hand-computed validation established the load-bearing finding: the Wilson bound alone does NOT solve small-number noise (a 2→10 repo's bound of 0.490 beats a 4,000→4,300 repo's 0.0625). Only the floor and the bound together produce the intended ordering, so both must be encoded as tests, not just documented.

Output: `python -m techtrend.score` populates the scores table, and the dashboard's velocity column stops rendering placeholders.
</objective>

    Create `techtrend/pipeline/score.py` exposing `Z_SCORE_95 = 1.96`, `CURRENT_SCORE_VERSION = 1`, and three functions plus a driver.

    `wilson_lower_bound(successes: int, n: int, z: float = Z_SCORE_95) -> float` implements the standard Wilson score interval lower bound exactly as given in RESEARCH.md Pattern 3. Return 0.0 immediately when n is less than or equal to 0. Floor the result at 0.0 so a negative can never be returned.

    `score_entity(stars_gained: int, stars_total: int, floor: int) -> tuple[bool, float]` returns `(eligible, bound)`. Return `(False, 0.0)` when `stars_gained` is strictly less than `floor` or when `stars_total` is less than or equal to 0 — the floor check runs FIRST, before any bound is computed. This ordering is the entire mitigation for small-number noise; inverting it reintroduces the exact defect RESEARCH.md validated against. Clamp `successes` to `min(stars_gained, stars_total)` so the proportion cannot exceed 1.0. Compare integers directly; do not coerce to float before the floor comparison.

    `compute_window_gain(conn, entity_id: int, window_days: int) -> WindowGain` returns a small dataclass carrying `stars_gained`, `stars_total`, and `window_days_actual`. It reads all `snapshots` rows for the entity with `metric_name='stars'` within the trailing window, computes gain as `MAX(metric_value) - MIN(metric_value)` across the available rows regardless of whether `source_kind` is `observed` or `backfill`, and sets `window_days_actual` to the actual span of days observed — which may be fewer than `window_days` for a fresh entity. Return zeros with `window_days_actual` of 0 when the entity has no snapshot rows. Recording the ACTUAL span rather than the configured one is what makes a 1-day observation distinguishable from a 7-day one downstream; substituting the configured value here would silently overstate confidence.

    `rescore_all(conn, config, run_date) -> int` deletes existing rows for `CURRENT_SCORE_VERSION` at this `run_date`, then for each non-dormant entity computes the window gain, routes the raw metric through `momentum_for_source`, applies `score_entity`, and inserts a `scores` row carrying `entity_id`, `run_date`, `score_version`, `stars_gained`, `window_days` (the actual span), `wilson_lower_bound`, and `eligible`. Rows at other `score_version` values are left untouched so a formula regression can be compared against the prior version. Store the bound as a plain Python float with no rounding; formatting for display is the template's concern. `rescore_all` performs no network I/O and reads no state other than `entities` and `snapshots` — it must never consult the previous run's ranking, because doing so would make scores order-dependent and destroy the property that re-scoring is free.

    Create `techtrend/pipeline/normalize.py` implementing the D-13 seam. Expose `momentum_for_source(source: str, gain: int, total: int) -> tuple[int, int]` dispatching to a per-source converter that maps a raw metric onto a comparable `(successes, n)` momentum pair, and `GitHubMomentum` implementing that conversion for stars as the identity mapping. The point of this file is that Phase 3 adds Hacker News and npm by adding a converter here, not by editing `score.py`. Do NOT attempt to calibrate against HN points or download counts that have never been observed — D-13 says build the seam, calibrate later.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| snapshots table → scoring arithmetic | Star counts originate at GitHub and are attacker-influenceable in magnitude (fake-star campaigns are documented in PITFALLS.md); they reach numeric computation here |
| scoring output → dashboard ranking | The computed order determines what the user's attention is directed to |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-18 | Tampering | Purchased or botted stars inflating a repo's rank | medium | mitigate | The absolute floor plus the Wilson lower bound together suppress the small-sample manipulation that is cheapest to buy; a 7-day window prevents a single-day spike from dominating. This is mitigation, not elimination — detecting a well-funded fake-star campaign is out of scope for Phase 1 and is noted in PITFALLS.md |
| T-01-19 | Denial of Service | Integer overflow or division by zero in the bound computation crashing the score pass | medium | mitigate | `wilson_lower_bound` returns 0.0 for any n less than or equal to 0; Python integers are arbitrary precision so star counts cannot overflow; both paths are covered by passing tests |
| T-01-20 | Repudiation | A silently stale scores table after a failed scoring run | medium | mitigate | `techtrend/score.py` records a `failed` run_manifest row with error detail and exits non-zero, so the dashboard health strip can surface it |
| T-01-21 | Tampering | A formula change silently invalidating historical scores | low | mitigate | `CURRENT_SCORE_VERSION` keys every row; prior-version rows are retained rather than deleted so a regression is comparable against the previous formula |
| T-01-22 | Information Disclosure | Score computation reaching the network | low | mitigate | `rescore_all` performs no I/O beyond SQLite, enforced by an acceptance-criteria grep for HTTP client imports |
